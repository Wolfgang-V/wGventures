Field note

The homepage was firing eight simultaneous cart requests on load, tripping the database's connection-storm circuit breaker under free-tier auto-suspend. Both were invisible in the UI and fatal in production.

Fig. 2 — the diagram this whole site borrows from

  • A custom visualisation layer on Three.js rather than a full CAD kernel — the kernel bought precision a simulator never needed and cost load time it couldn't afford.
  • Part picking: click any component in the model to isolate and inspect it.
  • Exploded-view animation that pulls an assembly apart so you can see what sits behind what.
  • Highlighting driven directly by diagnostic output — the visuals are a function of the data, not hand-authored scenes, so a new fault definition renders without touching the 3D code.

Why I built it

I spent a decade doing hardware diagnostics before I wrote software for a living. What made a repair fast was never the error code — it was being able to picture where the fault sat inside the machine. AutoVerse is that habit turned into a tool.

Fig. 3 — the right tool being the smallest one

  • A full storefront in hand-written HTML, CSS and vanilla JavaScript — no framework, no bundler, no node_modules folder to go stale.
  • Responsive from phone to desktop, with the catalogue and product pages laid out on a CSS grid rather than a template kit.
  • Deploys as plain files, so the client can host it anywhere and keep it running without paying anyone a monthly platform fee.

Why static

Not every shop needs a framework. This one had a fixed catalogue and a client with no technical team, so a React build would have added a toolchain they couldn't maintain and a dependency tree that rots the moment nobody updates it. Plain files load faster, cost nothing to host, and will still open in a browser in five years. Choosing the smaller tool is a decision, not a shortcut.

Fig. 4 — designed for the market it actually serves

  • Wrote the Prisma schema first as the shared contract the whole build works against: price snapshotting on order items, Decimal on every money field, and an order status event trail for audit.
  • Designed for Osogbo specifically — landmark fields on addresses because street numbering is unreliable, phone-first identity, and cash on delivery as a first-class payment method rather than an afterthought.
  • A flat zone-to-zone delivery fee table instead of distance pricing, because riders quote by area, not kilometres.
  • Repo runs on protected main with PR review before merge and schema changes announced before the pull request.

Field note

The assumption going in was that this needed a native mobile app. It didn't. A PWA installs from a link shared in a WhatsApp group, skips the app store entirely, costs a fraction of the download on a metered data plan — and can still be wrapped for Play Store later without rewriting anything. Choosing the boring option bought months.

Field note

Deploying an Express API to serverless meant every cold start opened a fresh Mongo connection until the pool ran out. I cached the connection in global state so functions reuse it, and replaced the hardcoded CORS origin with dynamic whitelisting so local and production run against the same backend. It's also why I didn't move Planit to Next.js — websockets don't live on serverless, and a migration for its own sake isn't an improvement.

Fig. 6 — where I learned to write code that moves money

  • Account opening with token auth and OTP email verification, so no account goes active on an unverified address.
  • Fund transfers between accounts with balance validation before the write, and bill payments against a seeded biller catalogue.
  • Full transaction history with downloadable receipts.
  • Rate limiting and centralised error handling across every route, plus account management and settings.
  • Deployed frontend and API separately on Vercel, with CORS configured to serve local development and production from the same backend.

Field note

Money code doesn't get to be approximately right. Every transfer validates the balance before it writes, and every route returns a predictable error shape instead of leaking a stack trace to the client. This was the project where I learned that the interesting half of a banking app is everything that happens when a request fails.
